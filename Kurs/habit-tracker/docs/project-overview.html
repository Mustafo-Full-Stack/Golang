Habit Tracker — разбор структуры и работы проекта

Подробный путеводитель по каждой папке и файлу Go-проекта habit-tracker в его текущем состоянии: что уже написано, как слои связаны между собой, схемы работы и найденные нюансы.

1. Как проект работает НА ДАННЫЙ МОМЕНТ

✅ Что уже реализовано

  • Конфигурация: чтение ENV-переменных (internal/config).
  • База данных: создание пула подключений pgxpool.Pool и проверка Ping (pkg/db/postgres).
  • Схема БД: SQL-миграции для таблиц users, habits, habit_checks.
  • Доменные модели: структуры, валидация входных данных и стандартные ошибки (internal/models).
  • Авторизация (полный слой): регистрация (bcrypt), вход (проверка пароля + выдача JWT) и проверка токена (internal/service/auth + internal/repository/user).

🚧 Что сделано частично / пустое

  • Репозиторий привычек: есть только Create и ListByUser. Нет методов для отметки выполнения привычек (habit_checks), удаления или получения одной привычки.
  • internal/service/habit/: папка создана, но внутри пока нет файлов.
  • docs/: была пустой папкой (до создания этого HTML-разбора).

⛔ Почему нельзя запустить сервер сейчас

  • Нет точки входа cmd/.../main.go (нет func main()).
  • Нет транспортного / HTTP-слоя (handler / middleware / роутера), хотя в конфиге уже заложен HTTPPort.
  • Все текущие пакеты — это библиотечные модули: go build ./... компилирует их без ошибок, но исполняемого бинарника ещё нет.
🐞 Найденный баг в текущем коде: В файле internal/repository/habit/postgres.go на 30-й строке в SQL-запросе функции ListByUser опечатка в плейсхолдере PostgreSQL: написано WHERE user_id = 1$ вместо WHERE user_id = $1. Компилятор Go не проверяет SQL-строки, поэтому go build проходит, но при реальном вызове PostgreSQL вернёт синтаксическую ошибку.

2. Рисунки и схемы работы

Проект построен по классической слоистой архитектуре (Clean / Layered Architecture): Transport (ещё не написан) → Service → Repository → PostgreSQL, а модели и конфигурация пронизывают слои.

Обрати внимание на хорошую практику безопасности в Login: при несуществующем email ошибка ErrNotFound подменяется на ErrInvalidCredentials, чтобы нельзя было перебором узнать, зарегистрирован ли email.

Стрелка означает «импортирует» (import "..."). Циклических зависимостей нет: internal/models находится в основании графа и не зависит ни от БД, ни от сервисов.

📁 migrations/
Готово • 2 файла

Папка с SQL-скриптами создания таблиц в PostgreSQL. Миграции пронумерованы (001_, 002_), чтобы накатываться строго по порядку. На текущий момент это «up»-скрипты (создание таблиц), без откатов (down) и без встроенного раннера миграций в Go-коде.

📄 migrations/001_create_users.sql
SQL • Пользователи

Создаёт таблицу users и регистронезависимый уникальный индекс для email:

CREATE TABLE IF NOT EXISTS users (
    id BIGSERIAL PRIMARY KEY,
    name TEXT NOT NULL,
    email TEXT NOT NULL,
    password_hash TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE UNIQUE INDEX IF NOT EXISTS users_email_lower_uniq ON users (lower(email));

За счёт users_email_lower_uniq база данных сама не позволит зарегистрировать Test@mail.com и test@mail.com как двух разных пользователей.

📄 migrations/002_create_habits.sql
SQL • Привычки и отметки

Создаёт две связанные таблицы:

  • habits — список привычек пользователя (id, user_id, name, created_at). Внешний ключ user_id → users(id) ON DELETE CASCADE.
  • habit_checks — журнал выполнения привычки по дням (id, habit_id, date типа DATE). Ограничение UNIQUE (habit_id, date) запрещает отметить одну привычку дважды за один день.
📁 pkg/ → pkg/db/ → pkg/db/postgres/
Общий переиспользуемый пакет

По соглашению Go-проектов папка pkg/ хранит код, который не привязан к бизнес-логике конкретного приложения и может быть переиспользован в других проектах. Внутри вложены подпапки db/postgres/ для подключения к PostgreSQL.

📄 pkg/db/postgres/postgres.go
Готово • 47 строк

Отвечает за создание и проверку пула соединений к PostgreSQL через pgxpool:

  • type Config struct — хранит Host, Port, User, Password, Database, SSLMode.
  • New(ctx context.Context, cfg Config) (*pgxpool.Pool, error) — формирует строку подключения, открывает пул pgxpool.New и сразу проверяет реальную доступность БД через pool.Ping(ctx). Если пинг не прошёл — закрывает пул и возвращает ошибку.
  • (cfg Config) dsn() string — безопасно собирает URL вида postgres://user:pass@host:port/db?sslmode=... через стандартные net/url и net.JoinHostPort (корректно экранирует спецсимволы в пароле и работает с IPv6).
📁 internal/
Закрытый код приложения

Специальная папка в Go: компилятор запрещает импортировать пакеты из internal/ внешним проектам. Здесь живёт вся логика именно нашего трекера привычек: config, models, repository, service.

📄 internal/config/config.go
Готово • 53 строки

Загружает настройки приложения из переменных окружения (ENV) в структуру Config:

  • Load() (*Config, error) — парсит длительность токена JWT_TTL через time.ParseDuration, проверяет обязательность JWT_SECRET (без него вернёт ошибку), заполняет HTTPPort и вложенный postgres.Config.
  • getEnv(key, defaultValue string) — берёт значение из os.Getenv или возвращает значение по умолчанию, если переменная пустая.
📄 internal/models/models.go
Готово • 104 строки

Центральный доменный файл проекта: сущности БД, входные DTO с валидацией и список типизированных ошибок.

Сущности
User (ID, Name, Email, PasswordHash, CreatedAt)
Habit (ID, UserID, Name, CreatedAt)
HabitCheck (ID, HabitID, Date)
Входные модели + Validate()
RegisterInput: trim Name, lower+trim Email, пароль 8..72 байта (72 — лимит bcrypt).
LoginInput: lower+trim Email, оба поля не пустые.
CreateHabitInput: trim Name, от 1 до 100 рун (символов UTF-8).

Ошибки (sentinel errors): ErrNotFound, ErrInvalidInput, ErrPasswordTooShort, ErrPasswordTooLong, ErrInvalidCredentials, ErrUserExists, ErrInvalidToken, ErrForbidden, ErrAlreadyChecked. Наличие ErrForbidden и ErrAlreadyChecked уже заложено на будущее (для сервиса привычек и проверок прав доступа).

📄 internal/repository/user/postgres.go
Готово • 58 строк

Работает с таблицей users в PostgreSQL через *pgxpool.Pool:

  • NewRepository(db *pgxpool.Pool) *Repository — конструктор репозитория.
  • Create(ctx, u *models.User) error — вставляет пользователя (INSERT INTO users ... RETURNING id, created_at) и записывает сгенерированные ID и CreatedAt прямо в переданную структуру u. Если PostgreSQL возвращает код ошибки 23505 (нарушение уникального индекса по email), преобразует её в доменную models.ErrUserExists.
  • GetByEmail(ctx, email string) (*models.User, error) — ищет пользователя по lower(email) = lower($1). Если строк нет (pgx.ErrNoRows), возвращает models.ErrNotFound.
📄 internal/repository/habit/postgres.go
Частично + есть баг

Начальная реализация работы с таблицей habits:

  • NewRepository(db *pgxpool.Pool) *Repository — конструктор.
  • Create(ctx, h *models.Habit) error — сохраняет привычку в habits и заполняет h.ID и h.CreatedAt.
  • ListByUser(ctx, userID int64) ([]models.Habit, error) — выбирает все привычки пользователя, отсортированные по id.
⚠️ Ошибка в строке 30: Написано WHERE user_id = 1$ ORDER BY id вместо WHERE user_id = $1 ORDER BY id. Перед запуском нужно обязательно исправить 1$ на $1. Также в этом файле пока нет методов для habit_checks, удаления или получения привычки по ID.
📄 internal/service/auth/auth.go
Готово • 113 строк

Самый законченный бизнес-модуль на данный момент. Отвечает за регистрацию, логин и проверку JWT:

  • NewService(users *userrepo.Repository, jwtSecret string, jwtTTL time.Duration) *Service — принимает репозиторий пользователей и параметры JWT.
  • Register(ctx, in models.RegisterInput) — валидирует ввод, хеширует пароль через bcrypt.GenerateFromPassword (DefaultCost), создаёт пользователя через users.Create.
  • Login(ctx, in models.LoginInput) — валидирует ввод, ищет пользователя по email, сравнивает хеш пароля bcrypt.CompareHashAndPassword, при любой ошибке авторизации возвращает единую models.ErrInvalidCredentials, иначе выпускает JWT-токен.
  • Authenticate(tokenString string) (int64, error) — парсит токен, строго проверяет алгоритм (только HMAC, защита от атак с подменой алгоритма), проверяет валидность и срок действия, достаёт числовой userID из claims.Subject.
  • createToken(userID int64) (приватный метод) — создаёт jwt.RegisteredClaims с полями Subject (ID пользователя), IssuedAt, ExpiresAt и подписывает алгоритмом HS256.

5. Что логично делать дальше, чтобы проект ожил

Шаг 1. Починить и дописать Repository

Исправить 1$ → $1 в internal/repository/habit/postgres.go и добавить методы для habit_checks (отметить выполнение, история/проверка за дату, удаление привычки).

Шаг 2. Реализовать service/habit

Написать сервис, который принимает CreateHabitInput, вызывает Validate(), проверяет владельца привычки (возвращая ErrForbidden чужим) и работает с отметками.

Шаг 3. Добавить HTTP-слой и main.go

Сделать роутер и хендлеры (регистрация, логин, CRUD привычек, auth-middleware через auth.Service.Authenticate) и точку входа cmd/api/main.go, которая свяжет config → postgres → repos → services → HTTP server.
