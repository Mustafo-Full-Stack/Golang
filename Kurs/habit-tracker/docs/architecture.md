# Архитектура трекера привычек

Запуск и проверка описаны в [README.md](../README.md), контракт API — в [openapi.yaml](./openapi.yaml).

## 1. Слои

```text
Клиент
  → handler      разбирает HTTP, вызывает сервис, отвечает JSON
  → middleware   проверяет JWT и помещает id пользователя в контекст
  → service      применяет правила, использует bcrypt и JWT
  → repository   выполняет SQL-запросы к PostgreSQL
  → PostgreSQL   хранит users, habits и habit_checks
```

| Слой | Делает | Не делает |
|---|---|---|
| handler | Читает JSON, путь и заголовки; вызывает сервис; переводит ошибки в HTTP-коды | Не содержит SQL и бизнес-правил |
| middleware | Проверяет `Authorization: Bearer`, кладёт id пользователя в контекст | Не проверяет права на конкретную привычку |
| service | Валидирует входные данные, хеширует пароль, выдаёт JWT, проверяет владельца привычки | Не обрабатывает HTTP и не выполняет SQL |
| repository | Выполняет SQL-запросы и переводит известные ошибки PostgreSQL в ошибки models | Не принимает решений о доступе |
| models | Описывает структуры, входные данные с `Validate()` и общие ошибки | Не выполняет ввод-вывод |

```text
cmd/api/                 точка входа: app.Run()
internal/
  app/                   config → PostgreSQL → repositories → services → handler → сервер
  config/                настройки из переменных окружения
  handler/               handler.go, auth.go, habit.go, middleware.go
  models/                структуры, входные данные, валидация и ошибки
  repository/user/       SQL пользователей
  repository/habit/      SQL привычек и отметок
  service/auth/          регистрация, вход и JWT
  service/habit/         привычки, отметки и проверка владельца
pkg/db/postgres/         подключение к PostgreSQL
migrations/              SQL-схемы пользователей и привычек
docs/                    OpenAPI и описание архитектуры
```

Сборка приложения находится в `internal/app/app.go`. Слой обращается к соседнему слою, а HTTP-обработчики не обращаются к базе напрямую.

## 2. Проверка данных

Входные структуры `RegisterInput`, `LoginInput` и `CreateHabitInput` централизуют валидацию.

- Перед работой с базой service вызывает `Validate()`.
- Имя пользователя и название привычки очищаются от пробелов по краям.
- Email очищается от пробелов и приводится к нижнему регистру.
- Пароль должен занимать от 8 до 72 байт: bcrypt использует максимум 72 байта.
- Название привычки должно содержать от 1 до 100 символов Unicode.

## 3. Бизнес-правила

**Пользователи**

- Email уникален без учёта регистра благодаря индексу `lower(email)`.
- В базе хранится только bcrypt-хеш пароля.
- Неизвестный email и неверный пароль приводят к одной ошибке: `401 invalid email or password`.

**Авторизация**

- JWT содержит id пользователя в поле `sub`; срок действия задаётся `JWT_TTL`.
- Защищённые маршруты требуют заголовок `Authorization: Bearer <token>`.
- Отсутствующий, неверный или истёкший токен приводит к `401`.
- Чужая привычка возвращает `403`, несуществующая — `404`.

**Привычки и отметки**

- Привычки принадлежат создавшему их пользователю.
- Отметка ставится за текущую дату UTC.
- Уникальность пары `(habit_id, date)` не допускает повторную отметку; повтор возвращает `409`.
- Отметки возвращаются по дате по возрастанию.

## 4. Потоки запросов

### Регистрация

1. Handler декодирует JSON и создаёт `RegisterInput`.
2. Service вызывает `Validate()`, затем хеширует пароль bcrypt.
3. Repository добавляет пользователя в PostgreSQL.
4. Нарушение уникального индекса email превращается в `ErrUserExists` и HTTP `409`.

### Вход

1. Service проверяет `LoginInput` и нормализует email.
2. Repository ищет пользователя по email.
3. bcrypt сравнивает переданный пароль с хешем.
4. Service подписывает JWT и возвращает его.

### Работа с привычкой

1. Middleware проверяет JWT и помещает `userID` в контекст запроса.
2. Handler передаёт `userID` из контекста и данные привычки сервису.
3. Service проверяет владельца до чтения или создания отметки.
4. Repository выполняет SQL. `ON CONFLICT (habit_id, date) DO NOTHING` защищает от дублей даже при параллельных запросах.

## 5. Архитектурные решения

| Решение | Причина |
|---|---|
| JWT без хранения сессий | Для проверки токена не требуется запрос к базе |
| bcrypt | Замедляет подбор паролей при утечке базы |
| Уникальный индекс на `lower(email)` | Не допускает дубликаты email с разным регистром |
| Уникальность `(habit_id, date)` в базе | Защищает от повторных отметок при конкурентных запросах |
| Отметки по UTC | Сервер использует одну согласованную дату |
| SQL-файлы миграций | Схема создаётся при первом запуске контейнера PostgreSQL с пустым томом |

## 6. Ограничения

- Выхода из системы и отзыва уже выданного JWT нет; токен действует до `JWT_TTL`.
- Дата определяется по UTC, что может отличаться от местной даты пользователя.
- Ответы `403` и `404` позволяют различить чужую существующую привычку и неизвестный id; для учебного проекта это выбранное поведение.
- Docker применяет SQL-миграции автоматически только при первом создании базы на пустом томе. Изменённые миграции не запускаются повторно.
- Для реального развёртывания задайте уникальный секрет JWT и надёжный пароль PostgreSQL вместо значений примера.

## 7. Docker и Makefile

```sh
make up      # база и приложение в Docker
make logs    # логи приложения
make down    # остановить контейнеры, данные сохранить
make reset   # удалить контейнеры и данные базы
```

Для локального запуска API используйте `make db`, затем загрузите переменные из `.env` и выполните `make run`.
